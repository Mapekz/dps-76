# Architecture

How a build turns into a DPS number, and how the UI is wired around that computation. This
is the map `CLAUDE.md` and `DESIGN.md` point to instead of restating; see
`docs/agents/domain.md` for how the rest of the doc set relates to this one.

No `file:line` anchors here on purpose — line numbers go stale the moment a file is edited.
Every claim below is checked by `doc-citations.test.ts` against the real module tree, so a
path that goes stale fails CI instead of silently rotting. A point-in-time version with
precise line anchors is published as a companion Artifact; treat that one as a snapshot, this
one as current truth.

## Layer map

```
SeventySix.esm
  │  scripts/extract/ (esm CLI)
  ▼
src/data/{live,pts}/generated/*.json        — checked-in, regenerated by `bun run extract`
  │  + src/data/overrides/*                 — hand-maintained, survives regeneration
  ▼
src/data/dataset.ts  getDataset(mode)       — CHOKEPOINT 1: the one merge of generated + overlay
  ▼
src/lib/loadout.ts  resolveLoadout()        — CHOKEPOINT 2: the one bridge from @/data to @/lib/engine
  ▼
src/lib/engine/scenarios.ts  computeScenarios()
  ▼
src/state/useScenarioResults.ts  (useMemo wrapper)
  ▼
src/components/results/ResultsPane.tsx
```

Both chokepoints are deliberate, not incidental — ADR-0001 states the engine
(`src/lib/engine/*`) never imports from `@/data` directly; every value it sees arrives
through `resolveLoadout`'s `ScenarioInput`. ADR-0014 states an override is applied to a
record in exactly one place, which is what makes `dataset.ts` a safe single merge point.

`src/lib/suggest/evaluate.ts`'s suggestion sweep is a second, parallel consumer of the same
two chokepoints — it calls `resolveLoadout`/`computeScenarios` up to ~600 times per config
change, which is why `resolveLoadout` accepts an opt-in memoization `scope` (see
`loadout-memo.ts`) that every other caller omits.

## The calculation call chain

One user edit to `BuildState` reaches a rendered number through:

1. **`useScenarioResults`** (`src/state/`) — a `useMemo` keyed on `[state.player, state.enemy,
   mode]`, deliberately excluding `state.view`/`buildName` so cosmetic state doesn't trigger
   recompute.
2. **`resolveLoadout`** (`src/lib/loadout.ts`) calls its internal `assemble()`, which in order:
   1. Looks up the base `Weapon` from the merged dataset.
   2. Resolves enemy type ids for race-gated conditions.
   3. Derives gated conditions (`strangeInNumbers`, `classFreakRank`, …) once, so every
      downstream fold sees the same values rather than re-deriving them.
   4. Gathers modifiers from nine sources: perks, legendary perks, mutations + consumables
      (buffs), addictions, manual-uptime toggles, the public-team buff, the player baseline,
      target debuffs, and armor effects — **before** the effective weapon is built, so
      weapon-stat modifiers (Guerrilla Expert's reload speed, etc.) can fold into it alongside
      OMOD stats.
   5. Resolves equipped OMODs and calls `buildEffectiveWeapon` (`src/lib/engine/
      effective-weapon.ts`), which folds `WEAPON_STAT_BUCKETS`/`SUSTAIN_CHANCE_BUCKETS`
      (speed, auto state, reload, range, capacity, charge fields, AP cost) into weapon
      fields, materializes cross-damage-type components, and resolves explosion
      chase/suppression.
   6. Concatenates weapon-intrinsic modifiers + OMOD modifiers + the remaining
      (non-weapon-stat) loadout modifiers into one flat, interned `Modifier[]` list.
   `resolveLoadout` then calls `derivePlayerStats` (`src/lib/player-stats.ts`) to fold
   `SPECIAL_BUCKETS`, max HP, and derived skills; assembles the `player` view; resolves the
   target body part and enemy defenses; and returns one `ScenarioInput`.
3. **`computeScenarios`** (`src/lib/engine/scenarios.ts`) — a single linear pipeline (see
   "Essential vs. accidental complexity" below for why it stays one function): fire rate and
   range falloff computed once; Onslaught/Bullet Storm sustained-stack averages bootstrapped
   once via a flag-agnostic context and threaded through; per-scenario (Free Aim, VATS) hit
   computation via `computePaperDamage` (`paper-damage.ts`); VATS crit rate via
   `computeCritMeter` (`crit-meter.ts`); sustained DPS via `computeSustain` (`sustain.ts`);
   DoT via `computeDotDps`; VATS AP uptime via `computeApEconomy` (`ap-economy.ts`); enemy
   mitigation via `applyMitigation` (`mitigation.ts`) when a target is selected.
4. **`ResultsPane`** renders the emphasized `ScenarioResult` via `HeadlineStrip` →
   `ScenarioCard` (the card renders *inside* the strip, not beside it).

The suggestion sweep (`src/lib/suggest/evaluate.ts`) is the same chain run repeatedly: it
enumerates candidates, applies each as a `BuildAction` through the reducer, and diffs the
resulting snapshot against a baseline, all through the same two chokepoints above.

## The data reshapes

Five distinct shapes the data passes through after extraction, each a genuine IR change —
naming them is what keeps the pipeline from feeling like an unbroken blur:

1. **Merge** — generated JSON + `src/data/overrides/*` → one `Dataset` (`dataset.ts`).
2. **Assembly** — per-record `.modifiers: Modifier[]` fields, scattered across perks/OMODs/
   buffs/armor, concatenated into one flat per-loadout list (`loadout.ts`'s `assemble()`).
3. **Weapon rewrite** — a subset of that list gets consumed and rewritten into `Weapon`
   fields instead of staying modifiers (`effective-weapon.ts`) — modifier → field.
4. **Fold** — the remaining modifiers fold into scalars, one per bucket per context, via
   `resolve.ts`'s three fold primitives (`foldOps`/`foldBucket`/`foldBucketProduct`) —
   modifier list → scalar.
5. **Display shape** — scalars assemble into `ScenarioResult`/`ScenarioSet` for the UI, and
   separately into `DpsSnapshot`/`ScenarioHeadline` for the suggestion sweep — scalar → UI shape.

## Modifier IR reference

Every damage source (perk entry point, OMOD property, MGEF, legendary effect) normalizes to
one shape: `{ bucket, op: SET | MUL_ADD | ADD, conditions[], value | curveScale }`.

**The fold arithmetic** (`resolve.ts`'s `foldOps` — the one home for this rule):

```
result = (last SET ?? base) + (Σ MUL_ADD) × base + Σ ADD
```

Additive, not multiplicative — two +10% `MUL_ADD` entries give `1.2×base`, not `1.21×base`.
The one exception is the `spellMagnitude` regime (Field Surgeon's Stimpak-healing
multipliers), which composes as `∏(1 + MUL_ADD)` via the separate `foldBucketProduct`,
because it models Bethesda perk entry points that multiply rather than the additive
damage-pool convention every other bucket uses.

**Bucket regimes** (`BUCKET_REGISTRY`, `src/types/modifiers.ts`) — which fold mechanism
consumes a bucket, and whether the result reaches anything (`hasEngineEffect`):
`damageFold`, `dot`, `weaponStat`, `critEconomy`, `apEconomy`, `playerStat`, `bootstrap`,
`spellMagnitude`, `display`, or `unfolded` (no fold at all — a modeled-but-NYI mechanic).
`WEAPON_STAT_BUCKETS` (`effective-weapon.ts`) and `INERT_ENGINE_BUCKETS` (the picker's "no
effect yet" badge, `src/data/omods.ts`) are both *derived* from this registry, not
hand-maintained, so the picker cannot silently drift from what the engine actually wires. An
exhaustiveness test enforces every `Bucket` has a registry entry.

See `CONTEXT.md`'s **Bucket**, **Fold**, and **Bucket Regime** glossary entries for the
canonical wording; this section exists so the arithmetic itself has exactly one other stated
copy, not a fourth one.

## UI flow

```
main.tsx
  └ App.tsx: ThemeProvider → GameModeProvider → BuildProvider → PersistenceGate → AppShell
```

`BuildProvider` holds one `useReducer`, split into `BuildStateContext`/`BuildDispatchContext`
so state reads and dispatch don't force unrelated re-renders. `makeBuildReducer(mode)` is
re-memoized when `GameModeContext`'s mode changes — mode is a reducer-factory parameter, never
a `BuildState` field (ADR-0002).

`AppShell` mounts `Header` + `BuildColumn` (the accordion: Weapon → Armor → SpecialLoadout →
Team → Mutations → Conditions → Chems → FoodDrink → Magazines → Bobbleheads → Target) +
`ResultsPane`.

**Three side paths off the same `BuildState`**, each solving a distinct performance problem:

- **Suggestions worker** (`useSuggestions.ts` + `suggestions.worker.ts`) — debounces 300ms,
  posts the whole state to a dedicated `Worker` running `evaluateSuggestions` off the main
  thread, and applies only the response matching the *latest issued* request id (not latest
  *applied* — stale responses are dropped even if they arrive last).
- **Hover-diff cache** (`useHoverDiff.ts`) — a module-scope `WeakMap<BuildState, Map<GameMode,
  ...>>` shared by every `<ActionDelta>`/`<DiffTooltip>` in one open picker, so a combobox
  with dozens of options pays for one `resolveLoadout`/`computeScenarios` baseline instead of
  one per option. Synchronous (~5µs benched) — the worker is for the sweep, this is for
  per-option deltas.
- **Persistence** (`usePersistence.ts` + `src/lib/persist/codec.ts`) — URL hash first,
  localStorage fallback, 400ms-debounced autosave to both, via a versioned wire codec whose
  encode-side diff baseline and decode-side seed must be the same object
  (`createDefaultBuildState()`).

## Essential vs. accidental complexity

Real game mechanics that must not be "simplified" away:

- **The three-op fold algebra** — a faithful encoding of Bethesda's own OMOD property
  function types, not an arbitrary design choice.
- **The three-branch explosive-twin mechanism** in `paper-damage.ts` — the game itself
  implements three distinct explosion formulas (Curve-Table, Projectile-Scaling,
  chain/stream-suppressed); the branch mirrors three real mechanics.
- **The ~39-kind `Condition` union** — each variant maps to a real Bethesda condition-function
  shape (`GetIsRace`, `HasKeyword`, `WornApparelHasKeywordCount`, …).
- **`mgef.ts`'s size** — a necessary 1:1 routing table from ~150+ distinct MGEF/AVIF/entry-point
  identifiers to formula buckets.
- **The stack-simulation modules** — each implements a genuine steady-state model for a
  distinct mechanic (ADR-0005 records why "sustained average" beats "max stacks" as a
  default).
- **`loadout-memo.ts`'s memoization** — a measured, benched performance requirement for the
  ~600-candidate suggestion sweep, not premature optimization (ADR-0011 records a *different*
  optimization that was rejected on cost/benefit grounds).
- **`computeScenarios`'s length** — the function is long because it is a linear,
  compute-once-then-thread pipeline over real per-mechanic local state (fire rate, range
  falloff, stack caps, body-part geometry); splitting it costs 10-parameter signatures or an
  invented context object in exchange for no reduction in what a reader has to hold in mind.
  See ADR-0016 for the general rule this instance falls under.

Accidental complexity — structural, not mechanical, and the target of the simplification
pass this doc accompanies: the trace-collection boilerplate repeated at each fold call site,
memoization wrappers interleaved with domain composition in `loadout.ts`, and a small number
of duplicated component/dialog patterns in `src/components/build/*`.
